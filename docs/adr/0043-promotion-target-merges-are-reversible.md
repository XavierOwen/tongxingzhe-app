# 推广对象合并必须可逆

## 决定

合并不物理删除、匿名化或改写原对象。active merge 的普通目录只显示保留对象标识和逐字段来源组成的合并视图。授权查询仍能审查两个原对象及其来源。

原字段、创建来源、assignment、项目关系及修订、接触关联、个人与机构关系和其他既有历史继续绑定原对象。同一项目的关系、阶段、生命周期和备注按来源对象分开展示和操作。合并不计算统一阶段，也不覆盖任一原关系。

active merge 期间，所有目标相关 writer 都必须识别当前合并代次。writer 把新增或修订事实绑定该代次和已知来源对象。无法安全绑定的写入失败关闭。既有按对象 ID 写入的入口和旧客户端不能绕过该要求。

拆分把合并前事实和已有明确来源的合并期间事实自动归回原对象。其余合并期间事实必须逐项分配给一个原对象。确认在锁后验证 active merge、两端状态、授权和待处理事实清单。遗漏、漂移或任一写入失败使整次拆分零变更。拆分结束 active merge，但保留 merge、split 和事实分配历史。

手动匿名化任一成员、结束其最后 active assignment 或再次合并前，必须先拆分。合并本身不续期。active merge 的保留截止取两个成员当前截止时间中较早者，并进入既有的到期前三十天复核。继续保留需要在截止前分别明确续期即将到期的成员，系统随后重算较早截止。到期时仍未续期或拆分，retention writer 在一个事务中结束 merge，并按既有匿名化规则处理两个成员、本代次待分配事实和合并投影；它不阻断其他对象。任一清除失败使整个到期事务回滚。该处理不可逆，也不是拆分。

merge ledger 只保存 opaque 对象／事实标识、合并代次、字段来源指针和拆分分配状态，不复制或散列姓名、电话、email、备注、接触内容或其他事实值。现有 `personal_promotion_target_pii_export_v1` 继续分别导出符合原合同的 active 源对象，不应用合并视图。合并、拆分和精确重放使用固定 canonical payload 与客户端 request UUID。独立不可变审计不保存姓名、电话、email、备注、接触内容或错误原文。

## 后果

合并视图可以撤销，且不会把原事实改写成新的来源。数据库、Backend 和 Flutter 必须分别实现这些约束；本决定本身不证明合并或拆分已经可用。
